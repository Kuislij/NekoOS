# Текущая стратегия NekoOS

Обновлено 2026-09-30. Основная цель — пригодный для работы Linux-дистрибутив
на базе Arch с полноценным рабочим столом. По уточнённому запросу пользователя
берём совместимую готовую базу и бинарные пакеты из официальных репозиториев.
NekoOS развивает состав образа, оформление, настройки, выпуск и пользовательские
функции. Решение закреплено в [ADR-024](adr/0024-arch-derived-desktop-base.md).

## Системная и графическая основа

Основа — Arch Linux x86_64, glibc, systemd и pacman. Первый рабочий сеанс —
Xorg и Xfce: xfwm4, xfdesktop, xfce4-panel, xfce4-session, настройки,
Thunar и обычные приложения. Зависимости устанавливает pacman вместе
с программами. Собственные форматы NekoPkg/NSPKG и musl не смешиваются
с системным Arch-корнем.

Первый этап использует официальный `archlinux-bootstrap-2026.09.01-x86_64.tar.zst`.
Его закреплённая SHA-256:

```text
895661bdf6c64e91b7725874165fd05dd30c438d3ffec661671ab5cfb261ca58
```

Bootstrap проверяется также OpenPGP-подписью с полным fingerprint
`3E80CA1A8B89F69CBA57D98A76A5EF9054449A5C`. Официальная
[страница загрузки](https://archlinux.org/download/) и
[контрольные суммы релиза](https://archlinux.org/iso/2026.09.01/sha256sums.txt)
позволяют сверить эти входные данные.

Пакеты берутся из фиксированного снимка официальных репозиториев
`2026/09/29` в Arch Linux Archive. Это согласованный набор версий;
подписи пакетов обязательны. После установки нужен манифест фактических
версий и контрольных сумм артефактов. Выбор snapshot делает состав стабильным,
но ещё не доказывает побайтовую воспроизводимость образа. При подготовке
диска репозиторий переключается на обычное rolling-зеркало Arch для
гостевых полных обновлений. Перевод сборки на новый snapshot и обновления
гостевой системы проходят полную проверку.
Опции репозиториев и подписи описывает
[официальное руководство pacman.conf](https://man.archlinux.org/man/pacman.conf.5.en).

## Первый образ и среда сборки

Windows остаётся хостом, Ubuntu в WSL2 — средой подготовки, QEMU —
тестовой машиной. Дерево сборки располагается на Linux filesystem
`/home/neko/src/NekoOS`. Frontend запускается от обычного пользователя;
он проверяет bootstrap и вызывает root-помощник через WSL внутри Ubuntu
или sudo в обычном Linux. Помощник работает в отдельном пространстве
монтирования и готовит chroot, пакеты и новый файл диска.

Основной результат — **12 ГиБ GPT-диск**: раздел BIOS boot, EFI-раздел
256 МиБ, записываемый ext4-корень. Штатное ядро из пакета Arch, initramfs
от mkinitcpio и GRUB обеспечивают BIOS/UEFI-загрузку. EFI-загрузчик
устанавливается в removable-путь без записи UEFI-переменных хоста.
Для среды без loop-разделов остаётся явно отмеченный запасной ext4-образ
через `mke2fs -d`, загружаемый прямой передачей ядра и initramfs QEMU.
Основной ожидаемый режим — GRUB; прямой режим не означает готовность
загрузчика. Фактическая загрузка обоих путей требует теста.

```bash
bash os arch build
bash os arch test --no-build
bash os arch run --no-build
```

Эти команды относятся к новому пути. Обычные `bash os build/run/test`
сохранены для старого диагностического образа. Его `out/disks/state.img`
и `out/disks/system.img` продолжают хранить прежние файлы и не используются
как диски новой базы. Сборка публикует `out/arch/images/system-template.img`,
`vmlinuz-linux`, `initramfs-linux.img`, `packages.lock`, `snapshot.txt`
и `boot-mode.txt`; их шесть SHA-256 входят в `SHA256SUMS`.
Последний файл режима содержит `grub` или `direct`.
Первый обычный запуск создаёт `out/arch/disks/system.qcow2`, `system.json`
и независимый от новых сборок базовый `base-<SHA256>.img`. Пользовательские
изменения сохраняются в qcow2; резервная копия включает весь этот каталог.
Новая сборка шаблона сама по себе существующую VM не обновляет.
Перенос пользовательских файлов будет отдельной
проверяемой операцией после выключения гостевой системы.

Первая сборка Arch-образа завершена: 471 установленный пакет и отдельный
12 ГиБ GPT-диск с EFI/ext4 и GRUB, `boot-mode.txt` содержит `grub`.
Полный тест QEMU прошёл: две BIOS-загрузки и третья UEFI, видимые панели
и рабочий стол Xfce, менеджер окон, Thunar и отдельное окно Firefox.
Реальные события мыши и клавиатуры создали каталог через Thunar;
русский файл и его владелец проверены по SHA-256 до новых записей
на второй и третьей загрузках. Проверены glibc/systemd/pacman,
компиляция C-программы GCC, sudo и HTTPS из гостя; все три VM штатно
выключились. Этапы описаны в [плане](roadmap.md), подробные результаты —
в [отчёте](validation-arch-desktop-2026-09-30.md).

На Windows обычный запуск из `F:\NekoOS` — `.\Start-NekoOS.ps1`.
Этот скрипт использует Ubuntu, пользователя `neko` и Linux-копию
`/home/neko/src/NekoOS`; `-Build` собирает образ, `-Test` проверяет его,
`-Uefi` выбирает UEFI, `-Headless` скрывает окно обычного запуска.
На Ubuntu/Debian нужны `curl`, `gnupg`, `tar`, `zstd`, `util-linux`, `fdisk`,
`e2fsprogs`, `rsync`, `python3`, `qemu-system-x86`, `qemu-utils`;
`ovmf` нужен для UEFI. Файл диска разреженный, его виртуальная ёмкость
12 ГиБ. Текущие rootfs и кэш пакетов занимают примерно 5 ГБ,
дополнительно учитываются образы и сохраняемые изменения VM.

Профиль локальной разработки использует автоматический вход LightDM
в Xfce и обычный аккаунт `neko` с паролем `neko`; sudo запрашивает этот
пароль, root-пароль заблокирован. Гостевая сеть включена через
пользовательский режим QEMU. В serial-консоли ожидаемый признак готовности —
`NEKO_ARCH_READY`. Он подтверждает доступность консоли; готовность
полного desktop проверяется отдельно.

## Дальнейшие этапы

После рабочего сеанса добавляем и проверяем приложения, сеть, настройки,
обновления и резервное копирование. Далее — archiso-профиль для Live ISO,
установщик на отдельный виртуальный диск и проверки установленной системы.
BIOS/UEFI-загрузка первого GPT-диска уже прошла проверку в QEMU.
Archiso не является обязательной зависимостью первого дискового запуска QEMU.
Live ISO, установщик, физическое оборудование, звук и полный цикл обновлений
ещё не проверены. Настройка обычного rolling-зеркала в госте сама по себе
не подтверждает безопасное системное обновление.

В официальных репозиториях на 2026-09-30 доступен
[archiso 91-1](https://archlinux.org/packages/extra/any/archiso/).
Будущий профиль можно вести в проекте на основе `releng`; его штатный путь
`/usr/share/archiso/configs/releng` и интерфейс `mkarchiso` приведены в
[официальном руководстве](https://man.archlinux.org/man/mkarchiso.1.en).
Сайт руководства на дату проверки ещё показывает archiso 90, поэтому
параметры будущей сборки сверяются с установленной закреплённой версией.

Рабочий прототип Linux/BusyBox/musl с 51 системным пакетом и GTK3-заметкой
остаётся историей разработки и диагностическим стендом. Его успешные
[проверки](validation-gtk3-2026-09-30.md) сохраняются, но следующие desktop
этапы не требуют ручной пересборки его библиотек.
