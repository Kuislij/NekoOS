# Архитектура

Windows — хост. WSL2 — среда разработки. QEMU — отдельная тестовая машина.
NekoOS использует Linux kernel; собственная работа сосредоточена на сборке,
интеграции и пакетной инфраструктуре.

## Начальные решения

* Bash + Make: минимум зависимостей для первых коротких сценариев. Ninja
  проверяется как будущая зависимость upstream-проектов. При усложнении
  сборщика отдельно оценим Python и компилируемый язык.
* QEMU внутри WSL2 с TCG: единые Linux-пути, отсутствие зависимости от
  вложенной KVM. Цена — меньшая скорость. Windows QEMU пока не добавляем.
* Для этапа 2 предлагаем Linux + статический BusyBox + initramfs: меньше
  компонентов, чем GNU userspace. Это временный bootstrap, не окончательный
  выбор libc, init или набора утилит.
* Язык package manager отложен. Rust даёт memory safety ценой bootstrap
  toolchain; Go упрощает разработку, но требует своего toolchain; C/C++
  требуют больше ручного контроля памяти; Python добавляет runtime в ОС.
  Выбор закрепим перед MVP на основе ограничений базовой системы.

## Каталоги

| Путь | Назначение |
| --- | --- |
| `scripts/` | Короткие команды разработки |
| `docs/adr/` | Принятые архитектурные решения |
| `kernel/` | Будущие конфигурации ядра, не копия upstream |
| `rootfs/` | Исходный overlay, не собранный rootfs |
| `packages/` | Будущие собственные рецепты |
| `build/` | Временные сборки, staging rootfs и логи |
| `cache/sources/` | Архивы upstream |
| `cache/packages/` | Кэш бинарных пакетов |
| `out/repository/` | Сформированный репозиторий |
| `out/images/` | Образы для VM |

Генерируемые каталоги исключены из Git. Пока создаются только нужные для
проверок. Сборка host-программы не является сборкой target-userspace.
