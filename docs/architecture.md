# Архитектура

Windows — хост; WSL2 — среда разработки; QEMU — тестовая машина.
NekoOS использует upstream Linux, собственные настройки сборки, initramfs
и отдельный виртуальный диск для изменяемых данных.

## Текущий цикл

`configs/sources.sh` → HTTPS download/cache → SHA256 → подпись Linux →
извлечение → Linux/BusyBox/musl/TinyCC build → rootfs staging → cpio.gz → QEMU
→ serial log.
При обычном запуске QEMU также подключает `out/disks/state.img` как virtio-blk.
С флагом `--net` он подключает virtio-net к своей пользовательской сети:
BusyBox `udhcpc` получает адрес, гостевой DHCP-hook настраивает интерфейс,
маршрут и `/etc/resolv.conf`. Без флага виртуальная карта отсутствует;
loopback работает в обоих режимах.

Bash управляет короткими этапами, Make собирает upstream-компоненты,
Python 3 используется только на хосте для автоматизации теста. Сетевой тест
поднимает локальный HTTP-сервер в WSL и проверяет запрос из гостя без
обращения к внешним сайтам. В госте Python нет. Ninja пока нужен только для
проверки будущего host toolchain.

В госте `/init` монтирует proc/sys/devtmpfs/devpts/tmpfs. При запуске с диском
он монтирует ext4 в `/state` и привязывает его каталоги к `/root`, `/home`,
`/var/lib` и `/usr/local`. Если диск запрошен, но недоступен, загрузка
останавливается вместо запуска без сохранения данных. Затем управление
получает BusyBox init. Его `sysinit` вызывает `neko-service boot`: тот
по списку запускает встроенные службы и только после успеха печатает
`SYSTEM_READY`. Сейчас есть сетевая служба; команда `neko-service` позволяет
проверить и перезапустить её из консоли. `inittab` запускает shell на ttyS0
и восстанавливает его после выхода. Init также обрабатывает завершение
процессов и штатное выключение.

Rootfs хранит программы в `/usr/bin` и `/usr/sbin`; классические `/bin`,
`/sbin`, `/lib`, `/lib64` ссылаются на соответствующие папки в `/usr`.
Правила каталогов описаны в [filesystem.md](filesystem.md).

BusyBox и TinyCC статически связаны с закреплённой musl. Программы,
собранные TinyCC внутри гостя, используют ту же musl. При сборке на хосте
GCC выступает начальным компилятором и ищет заголовки и библиотеки в
`build/toolchain-root/`; его системная glibc не включается в эти бинарники.
Для быстрой разработки QEMU принимает ядро и initramfs напрямую. Второй путь:
виртуальный BIOS → GRUB с ISO → ядро Linux → `/init` → BusyBox init. Оба пути
используют один и тот же виртуальный ext4-диск с данными. Ядро Linux выполняет
раннюю настройку CPU, RAM, локального APIC, прерываний и ACPI, затем обнаруживает
virtio-blk. `/init` монтирует ext4. `neko-boot-status` проверяет наблюдаемые
признаки этих этапов уже после запуска. ISO пока загружается через BIOS;
постоянный системный rootfs и installer отсутствуют.

## Каталоги

| Путь | Назначение |
| --- | --- |
| `configs/` | Закреплённые источники и выбор applets BusyBox |
| `kernel/configs/` | Конфигурация x86_64 Linux |
| `boot/grub/` | Меню BIOS-загрузки с ISO |
| `rootfs/` | Исходные `/init`, `/etc`, DHCP-hook и гостевые команды; README не включается в образ |
| `scripts/`, `tools/` | Сборка, запуск, проверки |
| `keys/` | Закреплённый публичный ключ подписи Linux |
| `docs/adr/` | Архитектурные решения |
| `packages/` | Место для будущих собственных recipes |
| `cache/sources/` | Upstream-архивы и подпись |
| `build/sources/` | Извлечённые исходники |
| `build/linux-*`, `build/busybox-*` | Результаты компиляции ядра и BusyBox |
| `build/toolchain-root/` | Промежуточная установка заголовков, musl и TinyCC |
| `build/rootfs/` | Генерируемое дерево; пересоздаётся при сборке |
| `build/logs/` | Сборочные и serial logs |
| `out/images/` | Ядро, initramfs, BIOS ISO, конфигурации и hashes |
| `out/disks/` | Сохраняемый диск ext4; исключён из Git и не пересоздаётся при сборке |

Будущие `cache/packages/` и `out/repository/` отделены концептуально, но пока
не нужны. Генерируемые деревья не попадают в Git.

## Отложенные решения

Язык package manager: Rust даёт memory safety ценой bootstrap toolchain;
Go упрощает разработку, но требует отдельного toolchain; C/C++ требуют
ручного контроля памяти; Python добавляет runtime в guest. Выбор будет
сделан перед MVP. Формат пакетов, постоянный rootfs и расширение
системы сервисов пока не зафиксированы. См. ADR-002 о границах минимальной
загрузки, ADR-003 о структуре rootfs, ADR-004 о хранилище данных,
ADR-005 о C toolchain и ADR-006 о запуске служб.
