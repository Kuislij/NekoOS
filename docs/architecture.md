# Архитектура

Windows — хост; WSL2 — среда разработки; QEMU — тестовая машина.
С 2026-09-30 основная NekoOS использует бинарную базу **Arch Linux**:
glibc, systemd, pacman, штатное ядро и пакеты официальных репозиториев.
Графическая среда — **Xorg + Xfce + Thunar**. Состав образа, пользовательские
настройки, оформление и проверяемый процесс выпуска принадлежат NekoOS.
[ADR-024](adr/0024-arch-derived-desktop-base.md) заменяет прежнюю стратегию
ручной сборки полного рабочего стола на musl.

С 2026-10-01 целевая архитектура расширена
[ADR-025](adr/0025-reliable-arch-and-multi-ecosystem-apps.md):
проверенные системные каналы с восстановлением, устойчивые источники,
единый центр приложений и отдельные среды зависимостей для Debian/Ubuntu,
затем RPM. Flatpak служит отдельным способом установки приложений.
Системную базу продолжает вести pacman. Live ISO собирается через archiso;
GitHub Actions должен выполнять сборку по запросу и проверки выпуска.
Это запланированные слои; далее описана действующая реализация VM.

## Основной цикл Arch

Официальный bootstrap 2026.09.01 → SHA-256 и OpenPGP → Linux chroot →
pacman со снимком репозиториев 2026/09/29 и проверкой подписей →
штатные Linux/glibc/systemd/Xorg/Xfce/Thunar → настройки NekoOS →
mkinitcpio → GPT-диск с ext4, EFI и GRUB → BIOS/UEFI-загрузка QEMU → тесты
загрузки, графического сеанса и сохранения данных.

Новые команды `bash os arch build|run|test` отделяют этот путь от старых
`os build/run/test`. Arch-образ не должен подключать или заменять прежние
`out/disks/state.img` и `out/disks/system.img`. Для подготовки chroot нужны
Linux-права root; frontend выполняется от обычного пользователя и сам
вызывает вспомогательный процесс через WSL root либо sudo. Этот процесс
работает в отдельном пространстве монтирования. Исходники и временное
дерево располагаются на файловой системе WSL, а не на `/mnt/c` или `/mnt/f`.

В новой системе systemd запускает службы и графический вход, pacman ведёт
системную базу пакетов. Зависимости Xfce и приложений разрешаются средствами
Arch. Старые NekoPkg, NSPKG и musl-библиотеки не устанавливаются в этот корень.
Версии и фактический состав должны фиксироваться манифестом готового образа.
Фиксированный снимок ограничивает изменения зависимостей между сборками;
побайтовая воспроизводимость ещё требует отдельной проверки. Snapshot
используется при подготовке образа; гостевая конфигурация pacman затем
выбирает обычное rolling-зеркало Arch для полных обновлений.

Новый диск имеет размер 12 ГиБ и GPT: раздел BIOS boot, EFI-раздел
256 МиБ и основной ext4-раздел. GRUB устанавливается для BIOS и x86_64 UEFI
только на loop-устройство, связанное с создаваемым файлом. UEFI-установка
использует removable-путь без записи переменных firmware. При недоступных
loop-разделах подготовлен явно отмеченный прямой запасной режим.

В `out/arch/images/` публикуются `system-template.img`, `vmlinuz-linux`,
`initramfs-linux.img`, `packages.lock`, `snapshot.txt`, `boot-mode.txt`
и манифест SHA-256 этих шести артефактов. Кэш rootfs находится в
`build/arch/rootfs`, пакетов — в `cache/arch/packages`. Старые каталоги
системных образов остаются независимыми.

Первый пользовательский запуск создаёт `out/arch/disks/system.qcow2`
на основе `base-<SHA256>.img`, а `system.json` связывает их с режимом
загрузки. Базовый файл закреплён независимо от повторной сборки шаблона;
изменения гостя остаются в qcow2. Для резервной копии сохраняется весь
каталог `out/arch/disks`. Автоматическое обновление уже созданной VM
новым шаблоном пока не реализовано.

QEMU использует virtio-GPU, USB tablet, клавиатуру и virtio-net
в пользовательской сети. По умолчанию выбран BIOS; `--uefi` подключает
OVMF с отдельным временным файлом переменных firmware. Физические диски
и общие каталоги хоста не подключаются. LightDM настроен на автоматический
вход в Xfce от пользователя `neko`, serial-getty тоже открывает его сеанс
и печатает `NEKO_ARCH_READY`. Это отдельный признак готовности консоли,
а графический стек проверяется по работающим процессам, окнам и вводу.

Первая сборка завершена: 471 установленный пакет, `boot-mode.txt` — `grub`.
Полный тест прошёл две BIOS-загрузки и третью UEFI с одного временного
qcow2-диска. Проверены systemd, обычный пользователь и sudo, видимые панели
и рабочий стол Xfce, Thunar, Firefox, GCC, HTTPS, реальные устройства ввода
и сохранение файла до новых записей после повторных загрузок.
Результаты фиксирует [отчёт](validation-arch-desktop-2026-09-30.md).
Live ISO, archiso-профиль, установщик и полный цикл обновлений —
последующие задачи; физическое оборудование пока не проверялось.
Ниже описан уже проверенный musl-прототип.

## Диагностический musl-прототип

Он использует upstream Linux, собственные настройки сборки, initramfs
и отдельные виртуальные диски для системы и пользовательских данных.

### Цикл прототипа

Закреплённые источники в `configs/sources.sh` и `recipes/` → HTTPS
download/cache → SHA256 → подпись Linux → извлечение → сборка
Linux/BusyBox/musl/TinyCC и системных пакетов → rootfs staging → cpio.gz →
QEMU → serial log.
При обычном запуске QEMU также подключает `out/disks/state.img` как virtio-blk.
Опциональный режим `--system` сначала подключает `system.img`, затем тот же
`state.img` и загружает маленький bootstrap вместо полного initramfs.
С флагом `--net` он подключает virtio-net к своей пользовательской сети:
BusyBox `udhcpc` получает адрес, гостевой DHCP-hook настраивает интерфейс,
маршрут и `/etc/resolv.conf`. Без флага виртуальная карта отсутствует;
loopback работает в обоих режимах.

Bash управляет короткими этапами, Make и Meson собирают upstream-компоненты.
Python 3 используется только на хосте для сборки пакетов и тестов. Сетевой тест
поднимает локальный HTTP-сервер в WSL и проверяет запрос из гостя без
обращения к внешним сайтам. В госте Python нет. Ninja, закреплённый Meson,
xcb-proto и pkgconf используются на хосте для сборки графических библиотек.

В обычном режиме `/init` монтирует proc/sys/devtmpfs/devpts/tmpfs. При запуске с диском
он монтирует ext4 в `/state` и привязывает его каталоги к `/root`, `/home`,
`/var/lib` и `/usr/local`. Если диск запрошен, но недоступен, загрузка
останавливается вместо запуска без сохранения данных. Затем управление
получает BusyBox init. Его `sysinit` вызывает `neko-service boot`: тот
по списку запускает включённые встроенные службы, затем включённые локальные
скрипты из `/usr/local/etc/neko/services`, и печатает `SYSTEM_READY`.
Настройки автозапуска хранятся в `/var/lib/neko-services`. Ошибка отдельной
службы отмечается в `/run/neko/services` и выводится в консоль, не блокируя
доступ к shell. Для долгоживущих служб диспетчер отслеживает процесс и
выполняет остановку и перезапуск; короткие старые скрипты сохраняют прежний
контракт. При наличии framebuffer встроенная служба `desktop` запускает
`neko-session`, который передаёт `/usr/bin/neko-desktop` непривилегированному
пользователю `neko` (UID/GID 1000). Служба отслеживает этот процесс и
управляет его остановкой и перезапуском. `/init` готовит `/home/neko` и
даёт этому пользователю доступ к `/dev/fb0` и устройствам ввода QEMU.
`neko-desktop` пока является одним процессом, который получает события evdev,
управляет расположением и порядком окон и рисует их в framebuffer. Встроенные
окна Files, System, About и Help не запускаются как отдельные программы.
Файловая модель ограничивает действия деревом `/home/neko`; системное окно
читает сведения о ядре, процессорах, памяти, времени работы и корневом диске.
В оболочке намеренно нет графического терминала. Без framebuffer служба
пропускается. Loopback поднимает `/init` независимо
от сетевой службы. `inittab` запускает shell на ttyS0
и восстанавливает его после выхода. Init также обрабатывает завершение
процессов и штатное выключение.

В режиме `--system` первый `/init` из `bootstrap.cpio.gz` монтирует ext4
`/dev/vda`, переносит proc/sys/dev в новый корень и выполняет `switch_root`.
Затем полный `/init` с диска подключает прежний диск данных как `/dev/vdb`
и продолжает тот же процесс загрузки. Системный диск записываемый:
`/etc` и базовая часть `/usr` сохраняются между запусками. Сборка создаёт
новую заготовку, но уже созданный `out/disks/system.img` не заменяет. Явное
`bash os system-update` обновляет копию диска через специальный initramfs,
проверяет загрузку с отдельным временным диском данных и атомарно переключает
образ после создания резервной копии; `system-rollback` возвращает её.

Rootfs хранит программы в `/usr/bin` и `/usr/sbin`; классические `/bin`,
`/sbin`, `/lib`, `/lib64` ссылаются на соответствующие папки в `/usr`.
Правила каталогов описаны в [filesystem.md](filesystem.md).

Для базовой графической среды введён отдельный формат системных пакетов
`NSPKG/1`. Хостовый инструмент `tools/system_package.py` создаёт архив из
дерева `usr/` с каноническим манифестом: имя, версия, архитектура, лицензия,
SHA-256 исходника, заявленные зависимости и перечень файлов с их суммами.
При сборке образа он проверяет архивы, архитектуру, минимальные версии
зависимостей и их циклы, а затем устанавливает их в `/usr`. Опасные пути,
выходящие из дерева ссылки и замещение существующих файлов запрещены.
В проверенном образе установлен 51 системный пакет; его initramfs содержит
7701 запись. Манифесты пакетов хранятся в
`/usr/share/nekoos/system-packages/`. В образ входят Pixman 0.46.4,
xorgproto 2025.1, xtrans 1.6.0, libXau 1.0.12, libXdmcp 1.1.5,
libxcb 1.17.0, libX11 1.8.13, libXext 1.3.7, libXrender 0.9.12,
libXfixes 6.0.2 и libXrandr 1.5.5. Разделяемые библиотеки
собраны против musl NekoOS; xtrans поставляет фрагменты транспорта,
включаемые при сборке Xlib, а не отдельную библиотеку времени выполнения.
К очереди системных пакетов добавлены самостоятельно собранные zlib 1.3.2,
libxkbfile 1.2.0, xkbcomp 1.5.0, xkeyboard-config 2.48,
libfontenc 1.1.9, libXfont2 2.0.9, font-misc-misc 1.1.3,
libxcvt 0.1.3, libpciaccess 0.19, libdrm 2.4.134 и libsha1 0.3,
а также Xorg 21.1.24, libevdev 1.13.7, mtdev 1.1.7,
xf86-input-evdev 2.11.0, evilwm 1.5 и libffi 3.5.2.
Они обеспечивают XKB, битовые шрифты, вычисление видеорежимов,
доступ к PCI/DRM и SHA-1. `xkbcomp` и `cvt` — гостевые программы,
`xkeyboard-config` и `font-misc-misc` — данные. Рецепты используют
закреплённые исходники и не берут бинарные библиотеки из хостового Linux.
Следующий слой из исходников для musl составляют libpng 1.6.58,
Expat 2.8.5, PCRE2 10.48, GLib/GObject/GIO 2.84.4 и
libxfce4util 4.20.1. FreeType 2.14.3 и Fontconfig 2.17.1 вместе с
DejaVu 2.37 дают масштабируемые шрифты и их подбор. Cairo 1.18.6
предоставляет векторную отрисовку, PNG-вывод и X11-бэкенды; для GTK также
включены PDF, PostScript, SVG и сжатые потоки zlib. D-Bus 1.16.2
добавляет пользовательскую шину сообщений. Следующий слой составляют
GTK 3.24.52, Pango 1.56.4, HarfBuzz 12.3.0, FriBidi 1.0.16,
GdkPixbuf 2.44.8, libepoxy 1.5.10 и AT-SPI2 core 2.58.9 (ATK,
AT-SPI и atk-bridge). Для X11-бэкенда добавлены libXi 1.8.3,
libXcursor 1.2.3, libXinerama 1.1.6, libXcomposite 0.4.7,
libXdamage 1.1.7 и libXtst 1.2.5. Всё это собирается из закреплённых
исходников для musl. GTK3 использует программную отрисовку; libepoxy
предоставляет интерфейс диспетчеризации GL, а графический драйвер GL
остаётся отдельным будущим компонентом.
Тестовые программы вызывают функции Pixman, Xau/Xdmcp, XCB, Xlib и libXext
при загрузке в QEMU без X-сервера, а также проверяют GLib/GIO,
libxfce4util, PNG, XML, FreeType, Fontconfig и D-Bus. Отдельный тест
запускает Xorg на virtio-GPU
с программной отрисовкой, загружает evdev-драйверы клавиатуры и мыши и
подключает отдельный Xlib-клиент. `neko-x11-session` запускает Xorg,
а пользовательский `dbus-daemon`, evilwm и приложение `neko-gtk-welcome` —
отдельными процессами от пользователя `neko`; режим `bash os run --x11`
выбирает этот сеанс при загрузке. GTK3-приложение содержит русскую надпись,
PNG-изображение, текстовый редактор и кнопки сохранения и закрытия.
При несохранённых изменениях оно открывает модальный диалог с выбором
сохранения, отмены или выхода без записи. Заметка читается
и записывается через GIO по пути `/home/neko/Documents/Neko-note.txt`;
каталог `/home` сохраняется на `state.img`. Системные настройки GTK ищутся
в `/etc`, его GSettings-схемы компилируются при сборке пакета. Службы AT-SPI
активируются через пользовательскую шину D-Bus. Это промежуточный
X11-сеанс без полного Xfce. Основной рабочий стол, фон и панели теперь
работают в отдельном Arch-образе.
Решения описаны в
[ADR-017](adr/0017-system-packages-and-pixman.md) и
[ADR-018](adr/0018-x11-client-foundation.md); слой Xlib и следующий рубеж —
в [ADR-019](adr/0019-xlib-xext-and-xorg-milestone.md), серверные зависимости —
в [ADR-020](adr/0020-xorg-server-dependencies.md), а временный оконный сеанс —
в [ADR-021](adr/0021-window-managed-x11-session.md). Новый слой библиотек и
пользовательская шина — в [ADR-022](adr/0022-gtk-xfce-foundation.md),
а слой GTK3 и сохраняемая заметка — в
[ADR-023](adr/0023-gtk3-application-layer.md).

`neko-pkg` проверяет локальный архив до установки. Версии пакетов живут в
`/usr/local/lib/neko-pkg/store`, а активная команда — ссылка в
`/usr/local/bin`; оба пути сохраняются на виртуальном диске. Операции
сериализуются файловой блокировкой. NekoPkg/3 дополнительно открывает
ресурсы и библиотеки под `/usr/local/share/<имя>` и
`/usr/local/lib/<имя>`. Общий указатель активной версии переключает команду
и ресурсы одним переименованием. Оставшиеся после прерывания временные
каталоги и неактивные версии очищаются при следующем вызове. Зависимости
пока задают только минимальную версию уже установленного пакета.

BusyBox и TinyCC статически связаны с закреплённой musl. Программы,
собранные TinyCC внутри гостя, используют ту же musl. При сборке на хосте
GCC выступает начальным компилятором и ищет заголовки и библиотеки в
`build/toolchain-root/`; его системная glibc не включается в эти бинарники.
Для быстрой разработки QEMU принимает ядро и initramfs напрямую. Второй путь:
виртуальный BIOS → GRUB с ISO → ядро Linux → `/init` → BusyBox init. ISO
содержит два пункта: прежний initramfs и загрузку системного диска через
bootstrap; `bash os iso --system` выбирает второй по умолчанию. Оба пути
используют один и тот же виртуальный ext4-диск с данными. Ядро Linux выполняет
раннюю настройку CPU, RAM, локального APIC, прерываний и ACPI, затем обнаруживает
virtio-blk. `/init` монтирует ext4. `neko-boot-status` проверяет наблюдаемые
признаки этих этапов уже после запуска. ISO пока загружается через BIOS;
installer отсутствует. Для графической основы в ядре включены DRM/KMS
virtio-GPU, framebuffer и evdev. `--graphics` подключает экран, клавиатуру
и мышь в QEMU; `neko-desktop` рисует оконную оболочку напрямую в framebuffer.
Её окна пока существуют только внутри одного процесса, без протокола для
сторонних приложений. Их упрощённый вид задан кодом `neko-desktop`, а не
ограничением QEMU: virtio-vga уже передаёт изображение гостя в графическое
окно хоста. Системные пакеты и клиентские библиотеки X11 подготовлены
для проверки отдельных графических приложений в musl-rootfs.
Минимальный Xorg 21.1.24 с драйвером modesetting и теневым
framebuffer без зависимости от Mesa уже входит в образ. Его отдельный
Xlib-клиент работает в одноразовой VM. Существующая служба `desktop` остаётся
режимом по умолчанию. Опция `--x11` выбирает временный сеанс с evilwm и
отдельным приложением GTK3; после закрытия окна возвращается прежний
экран. QEMU подаёт координаты через `virtio-tablet-pci`: Xorg получает
абсолютные события evdev с явным `Option "Mode" "Absolute"`, а прежняя framebuffer-оболочка переводит их
в координаты экрана по диапазону устройства. Поэтому указатель работает
без захвата относительной мыши. Уже упакованы первые совместимые с musl
библиотеки, масштабируемые шрифты и D-Bus для пользовательского X11-сеанса.
Pango, GdkPixbuf, GTK 3.24 и необходимые им расширения X11 добавлены
в системный стек. Полный Xfce и Thunar на этом стенде не собраны.
Новый основной путь устанавливает их из совместимых готовых пакетов Arch,
с glibc, systemd и pacman; ручная сборка остальных musl-зависимостей
для него не требуется. Serial-консоль прототипа остаётся каналом
управления и диагностики. Актуальный курс записан в
[ADR-024](adr/0024-arch-derived-desktop-base.md), история прототипа — в

## Исторические отложенные решения musl-прототипа

Начальный `neko-pkg` написан на ash, который уже есть в BusyBox. Для будущего
автоматического получения зависимостей и полноценных транзакций потребуется
выбрать язык и runtime:
Rust, Go, C/C++ и Python имеют разные требования к bootstrap и размеру
гостевой системы. Дальнейшее расширение формата пакетов, более полное слияние
изменений постоянного rootfs и развитие системы сервисов за пределами
локальных скриптов
пока не зафиксированы.
См. ADR-002 о границах минимальной
загрузки, ADR-003 о структуре rootfs, ADR-004 о хранилище данных,
ADR-005 о C toolchain, ADR-006 о запуске служб, ADR-007 о первом пакете
ADR-008 о зависимостях и обновлении, ADR-009 о сохраняемых службах и
ADR-010 о системном диске, ADR-011 об обновлении с откатом,
ADR-012 об управляемых службах, ADR-013 о виртуальных графических устройствах,
[ADR-014](adr/0014-first-graphical-session.md) о первом графическом сеансе и
[ADR-015](adr/0015-windowed-desktop-path.md) об оконном прототипе и
[ADR-016](adr/0016-real-desktop-distribution-strategy.md) о готовом
графическом стеке, [ADR-017](adr/0017-system-packages-and-pixman.md)
