# Разработка

Добавлены Live ISO для пробной USB-загрузки и ручная сборка
на GitHub Actions. Следующий этап — проверенные обновления и восстановление,
устойчивые источники и единый центр приложений разных Linux-экосистем.
Курс и критерии: [ADR-025](adr/0025-reliable-arch-and-multi-ecosystem-apps.md)

Полная инструкция и границы Live-сеанса — [Live ISO](live-iso.md), результат

Старый `bash os iso` относится к musl-прототипу. Локальная среда WSL остаётся на F:.

## Основной путь с 2026-09-30

Развиваем NekoOS на базе Arch Linux: готовые официальные пакеты,
glibc/systemd/pacman и полный Xfce/Thunar. Новый интерфейс —
`bash os arch build|run|test`; подготовка Arch-rootfs выполняется в Linux
chroot с правами root. Сборки и диски нового пути отделены от существующего
musl-прототипа. Точные шаги и статус — в [стратегии](strategy.md) и
[плане](roadmap.md). Описанные ниже старые `os build/run/test` и запрет сборки
от root относятся к диагностическому прототипу.

Arch frontend тоже запускается от обычного пользователя, но сам вызывает
root-помощник через WSL либо sudo. На Ubuntu/Debian нужны `curl`, `gnupg`,
`tar`, `zstd`, `util-linux`, `fdisk`, `e2fsprogs`, `rsync`, `python3`,
`qemu-system-x86`, `qemu-utils`; для UEFI дополнительно `ovmf`.
Сборка выполняется в Linux-копии `/home/neko/src/NekoOS`.
12 ГиБ — виртуальная ёмкость разреженного GPT-образа; rootfs и кэш пакетов
текущей сборки занимают примерно 5 ГБ плюс образы и изменения гостя.
Результаты находятся в `out/arch/images`, пользовательская VM —
в `out/arch/disks`; эти каталоги исключены из Git.

Из Windows доступны `.\Start-NekoOS.ps1`, `-Build`, `-Test`, `-Uefi`
и `-Headless`. Первая сборка завершена (471 пакет), полный тест прошёл
две BIOS-загрузки и третью UEFI с Xfce/Thunar/Firefox.
Пройдены 57 unit-тестов; подробности — в
[отчёте Arch](validation-arch-desktop-2026-09-30.md).
В новой Ubuntu/Debian-среде `bash scripts/bootstrap-dev.sh --install`
устанавливает перечисленные инструменты, включая `fdisk`, `zstd` и OVMF.
Пакет [`fdisk`](https://packages.debian.org/trixie/fdisk) нужен для `sfdisk`,
который размечает только создаваемый файл GPT-образа.

Если `/dev/kvm` доступен запускающему пользователю на чтение и запись,
launcher автоматически выбирает KVM и CPU `host`; иначе — TCG и CPU `max`.
На текущем WSL-хосте доступность KVM проверена, пользователь `neko`
добавлен в группу `kvm`, новый Linux-сеанс получил доступ к `/dev/kvm`.
На другом Linux-хосте с доступным KVM при необходимости добавьте обычного
пользователя в эту группу и откройте новый сеанс:

```bash
sudo usermod -aG kvm "$USER"
```

Графический запуск сохраняет kernel/serial и stderr QEMU в
`build/logs/arch-run.log`; в терминале остаётся короткая информация
о запуске. `--headless` сохраняет вывод гостевой консоли в терминале.
Для проверки уже собранного образа используется
`bash os arch test --no-build --headless --uefi`.
Опция `--timeout SECONDS` меняет срок одной загрузки вместе с её проверками;
по умолчанию 480 секунд. Обычный тест делает две BIOS-загрузки,
с `--uefi` добавляет третью UEFI. Используется временный qcow2;
пользовательский `out/arch/disks/system.qcow2` не подключается к этому тесту.
Windows `.\Start-NekoOS.ps1 -Test` также прошёл две BIOS-загрузки
с видимым окном QEMU через WSLg. Обычный запуск допускает перезагрузку
из Xfce; для QA `-no-reboot` сохраняется.

## Рабочая среда

На 2026-09-30 Ubuntu WSL перенесена с C: в `F:\WSL\Ubuntu` штатным
механизмом WSL. Полная длина и SHA-256 виртуального диска совпали до и
после переноса. Linux-путь `/home/neko/src/NekoOS` сохранился;
крупные сборки, кэш пакетов и виртуальные диски теперь физически находятся
на F:. Сборка по-прежнему идёт внутри Linux filesystem WSL,
Windows-копия `F:\NekoOS` не заменяет её.

На 2026-09-23: Windows → WSL 2.7.14 → Ubuntu 26.04.1 LTS → QEMU 10.2.1.
После обновления WSL исчезла ошибка запуска `Wsl/Service/E_UNEXPECTED`.
Ubuntu зарегистрирована как WSL2. Создан обычный пользователь `neko`;
пароль ему не задавался, сборка не выполняется от root. Вход:

```powershell
wsl -d Ubuntu -u neko --cd /home/neko/src/NekoOS
```

`F:\NekoOS` — Windows-копия проекта; `/home/neko/src/NekoOS` — отдельная
сборочная копия на Linux filesystem. Изменения между ними не синхронизируются
автоматически. Перед редактированием другой копии проверяйте Git status;
после публикации используйте `git pull --ff-only` в чистой рабочей копии.
Сохраняемый диск находится только в Linux-копии по пути
`/home/neko/src/NekoOS/out/disks/state.img`; синхронизация исходников его
не копирует и не удаляет.
Режим `--system` использует второй файл `out/disks/system.img`; синхронизация
исходников и сборка также не заменяют его.
Команда `bash os system-update` переносит новую сборку на временную копию
выключенного диска, проверяет её загрузку и оставляет прежний диск в
`out/disks/system-backup-...img`. `bash os system-rollback ИМЯ` возвращает
выбранную копию. Диск данных `state.img` при проверочной загрузке не
подключается. Используйте команды только в той Linux-копии проекта, где
находится нужный `system.img`.

Зависимости musl-прототипа перечислены в `scripts/bootstrap-dev.sh`. Установка требует
root только внутри Ubuntu. Для уже созданного пользователя без sudo можно
из PowerShell выполнить:

```powershell
wsl -d Ubuntu -u root -- bash /home/neko/src/NekoOS/scripts/bootstrap-dev.sh --install
```

Обычные команды `os build/run/test` выполнять от `neko`. Для новых машин
использовать стандартную Ubuntu/Debian-учётную запись с sudo и quick start
из README. Скрипты не включают компоненты Windows и не перезагружают хост.

## Проверки этапов

Этап 1 проверен: `bash os check` дважды собирает и запускает C-программу
через Make/Ninja, затем запускает и закрывает QEMU без дисков.

Этап 2: `bash os test` проверяет реальные `bzImage` и `initramfs`, ждёт init,
выполняет команды в ash, проверяет proc/sys/dev/devpts/tmp и выключение VM.
После этапа 3 тот же тест проверяет структуру cpio, права и устройства,
повторный запуск shell после `exit`, ссылки `/bin` → `/usr/bin` и работу
команды `neko-help`. После добавления C toolchain он также компилирует и
запускает программу с `<stdio.h>` внутри гостя. Для интерактивного запуска
`bash os run` сокращает вывод ядра; `bash os run --verbose` оставляет полный
вывод. Обычный запуск
подключает сохраняемый ext4-диск; `--ram` отключает его. Отдельный
`bash os test --disk` проверяет файл через две загрузки и штатное выключение.
Запуск ограничен 90 секундами; другой срок: `bash os test --timeout 120`.
Проверка `--no-build` сначала сверяет SHA256 образов. Параллельные сборки и
параллельные boot-тесты блокируются, чтобы не смешивать результаты. Запуск с
диском также получает эксклюзивную блокировку, чтобы две VM не записывали
в один образ одновременно.

`bash os test --package` создаёт отдельный временный ext4-диск. Четыре загрузки
проверяют отклонение повреждённого архива, совместимость со старой установкой,
зависимости, обновление, сверку хеша, многофайловый ресурс, удаление и очистку
после нового запуска.
Пользовательский `out/disks/state.img` этот тест не подключает.
`bash os test --services` также проверяет управляемый фоновый процесс: запуск,
обнаружение работающего PID, остановку и перезапуск.
`bash os test --system` создаёт два временных диска и за две загрузки проверяет
переход на ext4-rootfs и сохранение изменений в `/etc` и `/root`. Рабочие
`state.img` и `system.img` он не подключает.
`bash os test --iso --system` использует те же временные диски и проверяет
полный путь через BIOS и GRUB; рабочие диски также не подключаются.
`bash os test --system-update` проверяет на отдельных временных дисках
обновление системной программы, сохранение изменённого `/etc`, доступность
пользовательских данных и откат прежней версии.
`bash os test --graphics` загружает virtio-GPU и устройства ввода без окна,
проверяя их узлы и графическую службу внутри гостя. Модели окон, файловых
действий и системных сведений можно отдельно проверить на хосте командой
`python3 -m unittest discover -s tests -p test_desktop_models.py -v`.
`bash os run --graphics` открывает окно QEMU с панелью и окнами Files,
System, About и Help; интерактивная командная строка остаётся на
serial-консоли терминала. Для ручной проверки файлового действия откройте
Files клавишей `F`, нажмите `N`, введите имя и подтвердите `Enter`. Созданный
файл должен появиться в `/home/neko` и пережить обычную перезагрузку с
диском данных. Графического терминала в оболочке нет.

Логи перезаписываются при следующем запуске. Не запускать интерактивную VM
и пересборку её образов одновременно. Для первого запуска используются
QEMU TCG, 1 CPU и 256 МБ гостевой RAM; вложенная KVM не нужна.

## Повторяемость и ограничения

Версии исходников и SHA256 закреплены в `configs/sources.sh`. Linux и musl
также проверяются по upstream OpenPGP-подписям с закреплёнными ключами.
У выпуска TinyCC 0.9.27 в официальном каталоге отдельной подписи нет;
для него используется HTTPS и закреплённый SHA256. Уже скачанные архивы
используются
повторно, но hash проверяется каждый раз. Несовпадение останавливает сборку;
повреждённый архив не заменяется автоматически. При намеренном обновлении
версии нужны новые проверенные hashes и повторный boot-тест.

Фиксированы SOURCE_DATE_EPOCH, имя сборщика, hostname и номер сборки ядра.
Сортировка cpio, владельцы и временные метки нормализованы. Host toolchain
пока берётся из Ubuntu: независимая воспроизводимость на других машинах
не гарантируется. Извлечённые исходники — локальный рабочий кэш; не менять
их вручную вместо project patches.

Сборка BusyBox 1.37.0 на GCC 15 выдаёт upstream warnings о const;
сборка и гостевой тест проходят. Это не готовый daily-driver userspace.
`make headers_install` создаёт заголовки Linux UAPI. musl и заголовки
устанавливаются в `build/toolchain-root/`; затем host GCC использует
созданный из musl specs файл `build/host-musl-gcc.specs` для статической
сборки BusyBox и TinyCC. TinyCC ищет заголовки и библиотеки для гостевых
программ по `/usr/include` и `/usr/lib`. Всё попадает в полный initramfs и
заготовку системного диска;
host `/usr` не меняется.

WSL сообщает о невозможности подключить диск E:. Он не используется проектом;
сборка работает в Linux filesystem. Настройки этого диска не изменялись.

Источники: [WSL](https://learn.microsoft.com/windows/wsl/basic-commands),
[Linux filesystem для сборок](https://learn.microsoft.com/windows/wsl/filesystems),
[QEMU](https://www.qemu.org/docs/master/system/invocation.html).
