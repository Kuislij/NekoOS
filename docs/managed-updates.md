# Управляемые обновления и откат в QEMU

NekoOS получает собственный менеджер версий системного диска. Он готовит
полное обновление официальных пакетов Arch на отдельной копии, проверяет
загрузку и рабочий стол в BIOS и UEFI и только затем разрешает её включить.
Предыдущий системный диск сохраняется для отката. Домашние файлы находятся
на отдельном ext4-диске и остаются текущими при смене версии системы.

Это первый вариант для VM, канал **testing**. Обновление на физическом
компьютере, stable-выпуск, автоматическое восстановление после неудачной
загрузки и графический интерфейс обновлений ещё предстоит разработать.

## Первый запуск

Выключите прежнюю NekoOS штатно через меню рабочего стола. Откройте
PowerShell в `F:\NekoOS`:

```powershell
.\Manage-NekoOS.ps1 -Action init
.\Start-NekoOS.ps1 -Managed
```

Инициализация копирует существующую Arch VM вместе с её домашними файлами.
Если обычная VM ещё не создана, используется проверенный шаблон Arch-образа.
Копия запускается дважды; импорт сверяет содержимое файлов, права,
владельцев, ACL и расширенные атрибуты через rsync. Файлы прежней VM
остаются в `out/arch/disks/`, новая VM — отдельно в `out/arch/managed/`.
Дальше домашние файлы этих двух VM развиваются независимо.

Все большие файлы остаются внутри Ubuntu WSL на F:, в Linux-копии
`/home/neko/src/NekoOS`. Повторять `init` для готовой VM не нужно.

## Обновление

Выключите управляемую VM. Проверьте её состояние и подготовьте обновление:

```powershell
.\Manage-NekoOS.ps1 -Action status
.\Manage-NekoOS.ps1 -Action prepare
```

Подготовка требует интернет и минимум **24 ГиБ свободного места** внутри
WSL. Это запас для временных копий; файлы разреженные и обычно занимают
меньше. Скачивание и две проверки рабочего стола могут занять несколько
минут. При успехе появится `NEKO_UPDATE_READY`, а состояние кандидата
станет `ready`. Текущая система и настоящий диск домашних файлов
при подготовке не изменяются: тестовая VM получает частную копию `/home`.

Включите проверенную версию и запустите рабочий стол:

```powershell
.\Manage-NekoOS.ps1 -Action activate
.\Start-NekoOS.ps1 -Managed
```

Для UEFI добавьте `-Uefi`. В терминале самой NekoOS команда
`neko-update status` показывает снимок пакетов и работающее ядро.

Первый зафиксированный кандидат — официальный архив **2026/10/01**.
Он обновляет 11 пакетов относительно базового образа 2026/09/29.
Следующие снимки добавляются в `arch/releases/testing.json` после проверки;
`prepare` не выбирает автоматически произвольную текущую версию Arch.

## Откат и очистка

Штатно выключите VM, затем:

```powershell
.\Manage-NekoOS.ps1 -Action rollback
.\Start-NekoOS.ps1 -Managed
```

Возвращаются прежние системные пакеты и настройки в `/etc` и `/var`.
Текущий `/home` сохраняется, в том числе файлы, созданные после обновления.
Повторный `rollback` переключает эти две версии обратно.
Откат системного диска не гарантирует обратную совместимость всех
пользовательских баз данных приложений после изменения их формата.

После ошибки подготовки старая система остаётся доступной. Можно удалить
только неактивный кандидат и повторить подготовку:

```powershell
.\Manage-NekoOS.ps1 -Action discard
.\Manage-NekoOS.ps1 -Action prepare
```

Удерживается одна предыдущая версия. Для следующего обновления сначала
нужно явно удалить её командой ниже — возможность отката к ней исчезнет:

```powershell
.\Manage-NekoOS.ps1 -Action forget-previous
```

Система не удаляет версии автоматически и не накапливает их без ограничения.
Не удаляйте `home.img` и не меняйте `state.json` вручную. Для резервной копии
выключенной VM сохраните **весь каталог** `out/arch/managed/`.
Если прервана первая инициализация, частично созданные файлы сохраняются;
`init` откажется их заменять. Сначала сохраните этот каталог для диагностики
и восстановления, затем создавайте новую VM отдельно.

## Проверки и границы

`prepare` выполняет полный `pacman -Syu`, сохраняет обязательную проверку
подписей пакетов доверенными ключами и сверяет SHA-256 баз `core` и `extra`
с закреплённым описанием выпуска. Неизвестные пакеты и попытка перейти на
снимок старше установленной версии останавливают операцию.
После установки пересоздаются initramfs и конфигурация GRUB. Проверяются
systemd, glibc, sudo, компиляция C-программы, HTTPS, видимые панели Xfce,
рабочий стол, Thunar и совпадение работающего ядра с установленным пакетом.

Переключение записывается атомарно с синхронизацией файла и каталога.
Неактивный диск сверяется с контрольной суммой перед активацией/откатом.
Симлинки, связанные для записи файлы и внешние backing/data-файлы
управляемых системных дисков отклоняются. Блокировка не позволяет
одновременно запустить эту VM и переключить её систему.

Контрольные суммы баз здесь закреплены в исходниках проекта; подписанный
каталог выпусков NekoOS, проверка свежести и несколько зеркал — дальнейший
этап. Отдельный тестовый `/home` обеспечивает сохранение текущих данных
при подготовке, но не является защитной песочницей от вредоносного пакета.
Root-права в госте и прямое использование pacman по-прежнему позволяют
обойти управляемый процесс; профиль предназначен для разработки.

Из Linux-копии команды имеют вид `bash os arch update ACTION`.
Полная автоматическая проверка запускается так:

```powershell
.\Manage-NekoOS.ps1 -Action test
```

Тест создаёт временную VM без доступа к дискам прежней/управляемой VM:
импорт `/home`, отказ сети, прерывание реальной ALPM-транзакции,
обновление, BIOS/UEFI, включение новой системы, создание каталога через
Thunar и откат с проверкой файлов и владельцев. Временные диски удаляются
по окончании; логи — `build/logs/arch-update-*.log`, итог —
`build/logs/arch-update-test-summary.json`.

[отчёт 2026-10-02](validation-managed-updates-2026-10-02.md).
