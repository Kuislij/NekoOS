# ADR-015: оконная оболочка и путь к отдельным приложениям

Статус: промежуточный прототип реализован; предложенный ниже путь через
собственный Wayland-композитор заменён
[ADR-016](0016-real-desktop-distribution-strategy.md). Дата: 2026-09-27.

Этот документ сохраняет первоначальное решение и описание работающего
прототипа. Актуальный курс — готовый графический стек Xorg/Xfce/Thunar с
отдельными процессами, а затем отдельная оценка Wayland и Hyprland.

Пользователю нужен рабочий стол, на котором можно открывать окна и работать с
файлами. Первый графический экран из [ADR-014](0014-first-graphical-session.md)
проверял вывод и ввод, но показывал только страницы одного приложения. Он не
давал привычных действий рабочего стола. Поэтому следующим шагом стала
оконная оболочка на уже работающем пути framebuffer и evdev.

`neko-desktop` запускается существующей управляемой службой `desktop` от
пользователя `neko`. Один процесс рисует фон, значки, панель и окна Files,
System, About и Help; он же обрабатывает мышь и клавиатуру. Модель окон
отвечает за положение, порядок, фокус, сворачивание и закрытие. Files работает
внутри `/home/neko`: показывает содержимое каталогов, ограниченный просмотр
текста, создаёт пустой файл или каталог и переименовывает обычный файл.
Файловые операции ограничены домашним деревом и не переходят по символьным
ссылкам. На этом этапе нет редактирования содержимого файла. System показывает
сведения, которые оболочка читает из работающего гостя, а не заранее
записанные демонстрационные числа. Изменения в `/home/neko` сохраняются при
запуске с диском данных. Графический терминал не является частью оболочки:
serial-консоль уже служит каналом управления и диагностики.

Это **оконный прототип, а не платформа графических приложений**. Окна Files,
System, About и Help не имеют отдельных процессов; сторонняя программа не
может создать своё окно. Здесь нет протокола Wayland, композитора, поддержки
`xdg-shell`, независимых клиентских буферов или управления дисплеем через
DRM/KMS из пользовательского пространства. Наличие DRM-драйвера в ядре не
означает, что оболочка уже использует DRM/KMS напрямую.

Следующий крупный этап строится поверх существующего запуска службы, учётной
записи `neko`, устройств ввода и виртуального GPU:

1. Добавить в сборку графические библиотеки и проверку небольшого клиента и
   сервера Wayland с тем же C toolchain и musl.
2. Реализовать композитор, который владеет экраном и вводом. Для первых
   отдельных приложений достаточно программных буферов `wl_shm` и ролей окон
   `xdg-shell`; Files и System должны стать самостоятельными процессами,
   которые получают ввод и передают изображение через этот протокол.
3. Перевести композитор с framebuffer на DRM/KMS, проверяя установку режима,
   смену буферов и восстановление после остановки процесса в QEMU. Затем
   расширять поддержку графических устройств и ускорения.
4. Добавить запуск и завершение приложений, упаковку их ресурсов, управление
   сеансом и проверки сохранения данных. Serial-консоль должна оставаться
   доступной, когда графическая служба недоступна или падает.

Промежуточная оболочка полезна сама по себе: она проверяет компоновку окон,
файловые действия и базовое взаимодействие пользователя. При этом её
внутренний интерфейс окон не объявляется публичным API. Для независимых
приложений он будет заменён стандартным графическим протоколом, а файловые
и системные модели можно будет переиспользовать отдельно от рисования.
